# Eligibility API (bounded first slice)

`GET /grants/{grantCallId}/eligibility` evaluates the current grant version for the applicant profile owned by the bearer project owner capability. `HEAD` has the same status and headers. The token is the same `Authorization: Bearer ...` capability used by `/applicant-profile`. Missing, malformed, revoked, and unknown capabilities receive the same 404 `OWNER_CAPABILITY_INVALID`. A missing grant receives 404 `GRANT_NOT_FOUND` after authorization.

The JSON response contains `grantCallId`, `versionId`, `ruleSetId`, `status`, `rootResult`, `reason`, `conditions`, `missingAttributes`, and `blockers`. Each condition has its ID, public attribute key, `PASS` / `FAIL` / `UNKNOWN` / `NOT_APPLICABLE`, a reason code, a blocking flag, rule `evidenceId`, and input source, verification status, and evidence ID where present. `blockers` lists the causal blocking condition IDs for a failed root, including passing children negated by `NOT`; an unverified causal condition cannot yield definitive `INELIGIBLE`. Raw profile values, expected values, source references, rule operators, group topology, and source text are omitted. The response uses `Cache-Control: private, no-store` and is recomputed from one read-only D1 batch of current version, rules, and owner profile per request; evaluation writes nothing.

No current rule set returns `NEEDS_REVIEW` with `NO_RULE_SET`. No owner profile returns `NEEDS_INFORMATION` with `NO_PROFILE` when the rule set is valid. More than one rule set, malformed trees, over-limit rows, unsupported operators/types, and malformed inputs/rules return `NEEDS_REVIEW`. A valid missing attribute yields `UNKNOWN` and `NEEDS_INFORMATION`; an explicit profile `UNKNOWN` is treated as missing. For a mapped attribute, a null or `UNKNOWN` profile column falls back to its sparse attribute value, if present. A non-null profile column takes precedence. Sparse fallback type and provenance must be valid; a verified sparse input requires an evidence ID, and conflicting sparse rows cause review. Missing values remain missing under `NOT_APPLICABLE` policy. Definitive `ELIGIBLE` and `INELIGIBLE` require both verified rules and verified, evidenced applicant inputs for the relevant blocking conditions. Profile columns are user declared, so their passing result is `LIKELY_ELIGIBLE` and their failing result is `NEEDS_REVIEW`, even when the rule is verified. A change to the owner's IČO atomically marks existing sparse facts `NEEDS_REVIEW` until they are verified for the new identity; a municipality-code change similarly invalidates sparse `applicant.municipality.*` facts, including population, without requiring an IČO change. A sparse `VERIFIED` value is trusted only if its `field_evidence` record is itself verified, identifies that exact applicant-attribute-value row and attribute key, and traces to an extracted official document (`OFFICIAL` or `OFFICIAL_OPEN_DATA`); a dangling, unrelated, quarantined or secondary-source reference fails closed to `NEEDS_REVIEW`. These status rules follow `packages/eligibility` with applicant input trust checked separately from rule trust.

This Workers subset evaluates applicant scalar `STRING`, `ENUM`, `GEO_ID`, `INTEGER`, `NUMBER`, `BOOLEAN`, `MONEY_MINOR`, and `PERCENT_BPS` values with `EQ`, `NEQ`, `IN`, `NOT_IN`, `EXISTS`, and `NOT_EXISTS`; numeric scalar values also support `LT`, `LTE`, `GT`, and `GTE`. It supports `AND`, `OR`, and `NOT`, blocking, and unknown policy. It reads frequently used applicant fields from `applicant_profiles` and sparse applicant attributes from `applicant_attribute_values`. Project attributes, geography hierarchy, dates, sets, ranges, and the remaining Python operators are outside this slice and cause review. Rule trees are limited to 64 groups, 128 conditions, 16 levels, and 128 sparse profile values; JSON values to 4096 characters and membership arrays to 64 items. No stored evaluations are introduced.

Search relevance, grant text, and the public grant-detail endpoint do not supply eligibility facts. This endpoint's evidence IDs are references to D1 provenance records; consumers may resolve grant evidence separately through the existing grant-detail API. Client-supplied profile provenance does not promote an input or a rule to verified.
