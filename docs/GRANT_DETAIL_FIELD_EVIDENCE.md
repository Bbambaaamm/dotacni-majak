# Doklady u financování a požadavků (#401)

Historická změna stavu se na detailu vysvětlí pro oba doložené zápisy pole `status` a `/status`; kanonický pointer `/status` už není skryt za pouhým obecným označením změny. Jiné cesty, neznámé hodnoty stavů ani jiný typ změny se jako přechod stavu nevykládají. Výklad zůstává historický, nikoli potvrzení dnešní otevřenosti nebo způsobilosti. Unit test chrání obě varianty i nesouvisející cesty; syntetický D1 → Detail API → mobilní Chromium test čte `/status` a kontroluje historické upozornění, a11y a reflow. Nejde o živé ověření výzvy.

Detail klient přijímá stav výzvy (i stav každé zobrazené historické verze) jen v kanonické osmici D1: `DRAFT`, `ANNOUNCED`, `PLANNED`, `OPEN`, `PAUSED`, `CLOSED`, `CANCELLED`, `ARCHIVED`. Neznámý stav v HTTP 200 se nesmí vykreslit jako přijatý stav výzvy; odpověď se celá skryje s retry. Prázdná kolekce známých požadavků nadále znamená UNKNOWN, nikoli zamítnutí způsobilosti; zachycené OPEN není garance dnešní otevřenosti. Unit regrese pokrývá obě hranice a všech osm povolených stavů, mobilní E2E syntetický D1/API detail, pozměněnou odpověď a retry k API s axe/reflow. Nejde o ověření živé výzvy.

Detail klient respektuje pevné limity Detail API: nejvýše 20 zdrojových záznamů, 100 dokladů, 20 změn a 20 verzí. Odpověď HTTP 200 s větší kolekcí se celá skryje s možností retry; klient nesmí přebytečné důkazy tiše oříznout ani prezentovat neověřený seznam jako úplný. Přesně na limitu a explicitní prázdné kolekce v režimu UNKNOWN zůstávají platné. Unit regrese pokrývá každou mez a mobilní E2E načte skutečný syntetický D1/API záznam, změní jen odpověď na 101 unikátních dokladů a po retry znovu použije skutečné API včetně axe/reflow. Ani tento guard nedokazuje úplnost zdrojových podmínek.

Detail klient přijímá u zdrojového záznamu jen stavy `SEEN`, `MISSING_CANDIDATE` a `CONFIRMED_MISSING`, které povoluje kanonické D1 schéma. Jiný stav z HTTP 200 nesmí být zaměněn za zrušení výzvy ani za doložené pozorování či potvrzené chybění; celá odpověď se skryje s možností retry. Prázdný seznam zdrojů zůstává dovolený a UI jej označuje jako nedoložený. Unit regrese ověřuje povolené i nepovolené hodnoty; mobilní E2E načte skutečný syntetický D1/API záznam, pozmění jeden stav v odpovědi a po retry znovu načte API včetně axe a reflow. Nejde o živé ověření výzvy u poskytovatele.

Detail klient odmítá opakovaná ID v jednotlivých kolekcích termínů, finančních scénářů, požadavků, dokladů a změn vrácených HTTP 200. Duplicitní řádek nesmí zdvojit důkaz či úkol ani vytvořit nejednoznačnou vazbu přes `evidenceId`; celá odpověď se bezpečně skryje a retry načte API znovu. Prázdné kolekce a stav UNKNOWN se nemění; zdrojové záznamy mohou mít více pozorování stejného zdroje, proto se tento guard na `sources` nevztahuje. Unit regrese zkouší každou kolekci; mobilní browser ověřuje nejprve skutečnou syntetickou D1/API odpověď, pozměněnou duplicitní odpověď a návrat k reálnému API včetně axe/reflow. Není to důkaz správnosti skutečných dotačních podmínek.

Detail klient u dokladů z HTTP 200 přijímá nepovinná čísla stran jen jako kladná bezpečná celá čísla; pokud jsou uvedeny obě meze, konec nesmí předcházet začátku. Chybějící jednotlivá mez zůstává neznámá, nikoli dopočítaná. Neplatná odpověď se celá skryje za bezpečnou chybou s možností opakování; uživateli se nezobrazí vymyšlená stránka dokladu ani přípravná akce. Unit test pokrývá 0, záporná, zlomková, přetečení a obrácené meze. Mobilní browser regrese nejprve přečte skutečný syntetický D1/API doklad na straně 2, pozmění pouze odpověď HTTP 200 na obrácené meze a po retry se vrací ke skutečnému D1/API; ověřuje také axe a reflow. Tento klientský guard nenahrazuje kvalitu zdrojových dat ani neprokazuje podmínky reálné výzvy.

Detail rozlišuje čas zachycení verze a poslední pozorování zdrojového záznamu. Poslední pozorování se vybírá podle skutečného okamžiku včetně UTC offsetu, nikoli podle textového řazení časových značek; stejně se vybírá `sourceCheckedAt` v přehledu pracovního prostoru. Neparsovatelná časová značka není důkazem pozorování. Výběr platí pro nejvýše 20 zdrojových záznamů vrácených Detail API, které se také řadí podle okamžiku; při dosažení limitu zůstává seznam označen jako omezený. Pozorování samo nepotvrzuje opětovné ověření podmínek ani aktuální možnost podat žádost. Regrese používá dva syntetické D1 záznamy s opačným textovým a chronologickým pořadím a skutečný API/browser/workspace tok včetně mobilního axe a reflow.

Detail výzvy zobrazuje vedle normalizovaného scénáře financování a požadavku odkaz na dokument, stránku a stav ověření, pokud `evidenceId` odpovídá důkazu v aktuální odpovědi Detail API. Odkaz vede na `sourceUrl` vrácenou API, nikoli na odhadnutou adresu. Pokud vazba chybí nebo důkaz není v omezené sadě odpovědi, text výslovně upozorní, že samostatný doklad není připojen, a odkáže uživatele na oficiální zdroj. Toto není posouzení individuální způsobilosti ani výpočet vlastní hotovosti.

Regrese používá syntetický D1 seed a skutečný API/DB → browser tok; ověřuje oba kontextové odkazy, chybějící doklad, mobilní reflow a automatickou a11y kontrolu. Syntetická částka není fakt o reálné výzvě. Důkazy z oficiálních zdrojů zůstávají rozhodující; limit API (100 evidence rows) může mít za následek explicitní stav bez připojeného dokladu.

Detail nyní ukazuje všech nejvýše 100 dokladů vrácených Detail API (dříve skryl vše za prvních 20). Při přesně 100 záznamech výslovně sděluje, že API má limit a další doklady mohou existovat; neoznačuje seznam za úplný. Syntetický D1 seed se 101 doklady ověřuje skutečný API cap, browser-visible poslední zobrazený doklad, mobilní reflow a a11y. Limit API a chybějící doklad nad limitem zůstávají známým omezením, nikoli důvodem považovat podmínky za splněné.

Pokud Detail API nevrátí žádný zdrojový záznam ani doklad, detail upozorní přímo u stavu výzvy, že výskyt u zdroje a poslední pozorování nejsou doloženy. Panel evidence netvrdí, že zdrojový záznam existuje; odkáže na ověření u poskytovatele. Kanonický stav OPEN se tím nemění a absence záznamu neznamená zrušení. Regrese ověřuje nulové `sources`/`evidence` proti skutečné D1/API odpovědi a browser text; není to nové ověření oficiálních podmínek.

Při fresh CI odhalil navazující mobilní test vyhledávání závod: opožděný `toggle` již odpojeného panelu mohl po obnovení výsledků přepsat stav nového panelu a skrýt řazení. Handler nyní přijímá událost jen od aktuálně připojeného panelu; E2E čeká na nové výsledky místo čtení starého DOM a znovu ověřuje viditelnost řazení. Jde o úzkou stabilizaci nutnou pro zelený gate, nikoli změnu parametrů vyhledávání.

Historie verzí na detailu má oddělený limit Detail API 20 položek: aktuální verze je vždy v seznamu, zbývající jsou nejnovější další verze. Při přesně 20 vrácených položkách UI uvádí „zobrazených“ a upozorní, že další verze mohou existovat, včetně mezilehlých starších než nejnovější verze, pokud se reaktivovala dřívější verze; nepřítomnost není důkaz, že nikdy nebyly publikovány. Syntetická D1 výzva s 22 neměnnými verzemi ověřuje API řazení a limit proti skutečnému API a mobilnímu browseru včetně a11y. Další syntetická reaktivace ukazuje aktuální verzi 1 i při limitu 20 a dalších 21 verzích. Úplná historie ani živé ověření podmínek tím nejsou zaručeny.

Rychlý přehled nyní u začátku a konce příjmu zobrazuje přesnou hodnotu `submissionOpenAt`/`submissionCloseAt` z Detail API včetně zdrojového času a offsetu, pokud je uveden. Datum bez času zůstane jen datem: UI nepřidá půlnoc ani lokální zónu. Sekce termínů dále rozlišuje strukturovaný termín a doklad. Regrese přes skutečné D1/API/browser ověřuje časový konec, datum bez času, mobilní reflow a axe; není to potvrzení, že je příjem stále otevřený.

Karta výsledku vyhledávání používá pro `submissionCloseAt` stejný formát: zachová čas a zdrojový offset, datum bez času i stav „Není uvedeno“. Neplatná hodnota zůstane beze změny. Real D1/API/browser regrese ověřuje časový konec v UTC i se zdrojovým offsetem `+02:00`, datum bez času a chybějící termín; zobrazený termín nepotvrzuje aktuální otevřenost výzvy.

Pokud Detail API nemá `officialDetailUrl` ani zdrojový záznam (`sources` je prázdné), ale poskytovatel má `officialUrl`, detail nabízí pouze obecný web poskytovatele. Odkaz je tak označen v panelu evidence i v hlavních/mobilních akcích; nejde o přímý odkaz na konkrétní výzvu ani o doklad její existence. Bez jakékoli adresy zůstává návrat k hledání. Syntetický seed `grant:e2e:date:only` s prázdným zdrojem a bez detailní adresy ověřuje reálný D1/API/browser tok na desktopu a mobilu včetně axe a reflow; datum ani obecný web nejsou potvrzením aktuálních podmínek.

Pokud nejsou normalizované termíny, Detail API odvodí souhrnné okno z přesných hodnot `submissionOpenAt`/`submissionCloseAt` zachycené verze. K tomuto syntetickému řádku nepřipisuje samostatnou časovou zónu zdroje (`timezone: null`): datum bez času nesmí získat půlnoc/UTC a offset uvedený přímo v hodnotě zůstává beze změny. Skutečně normalizovaný termín se svou zónou se nemění. Unit regrese kombinuje datum a `+02:00`; mobilní E2E nad syntetickým D1 ověřuje API, oba browser texty, axe a reflow. Nejde o živé potvrzení otevřeného příjmu.

Nutnost požadavku na detailu přijímá z HTTP 200 pouze kanonické hodnoty `REQUIRED`, `CONDITIONAL` a `RECOMMENDED`. Jiný řetězec se nesmí přes výchozí vykreslení změnit na „Doporučené“ a tím snížit význam povinného dokladu; detail se bezpečně skryje s možností retry. Prázdná kolekce požadavků zůstává explicitně `UNKNOWN`. Unit regrese pokrývá všechny povolené i odmítnuté hodnoty; mobilní browser ověřuje syntetický D1/API požadavek, pozměněnou HTTP odpověď a retry na reálné API včetně axe a reflow. Nejde o potvrzení skutečné povinnosti u poskytovatele.

Kanonické schéma finančního scénáře dovoluje v `paymentMode` libovolný řetězec nebo `null` (finanční výpočet má užší enum). Detail proto nepřepisuje nový či zdrojově definovaný nenulový režim na „Není doložen“: zobrazí jeho hodnotu jako jiný režim a vyzve k ověření způsobu platby u poskytovatele. `UNKNOWN`/`null` zůstávají nedoložené; prázdný řetězec vede k explicitní výzvě k ověření. Neřetězcová data v HTTP 200 jsou nadále odmítnuta s retry. Unit regrese chrání kanonicky platné hodnoty i odmítnutí chybného typu; mobilní E2E ověřuje skutečný syntetický D1/API scénář, pozměněnou hodnotu `CASH`, chybný typ a návrat k API s axe/reflow. Není to potvrzení živých podmínek výzvy.

Detail v rozbaleném seznamu dokladů používá název dokumentu jen tehdy, je-li neprázdný. Pokud schází, text odkazu výslovně říká „Doklad bez uvedeného názvu dokumentu“ místo zveřejnění interního `fieldPath`; bezpečná `sourceUrl`, stránka, datum stažení a stav ověření zůstávají beze změny. API stále poskytuje `fieldPath` pro audit a nezaměňuje chybějící název za chybějící doklad. Unit regrese i mobilní syntetická D1/API/browser regrese kontrolují původní auditní pole, adresu odkazu, text bez cesty, datum a axe/reflow; nejde o živé ověření podmínek.
