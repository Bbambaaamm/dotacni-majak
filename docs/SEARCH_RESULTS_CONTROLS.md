# Výsledky vyhledávání — globální stav, dostupnost termínu, datum uzávěrky a přesný poskytovatel (#400)

`/hledat` načítá z `GET /api/search` nejprve 20 výsledků v pořadí relevance; další stránky načte uživatel tlačítkem. Volitelný stav (`OPEN`, `PLANNED`, `ANNOUNCED`), dostupnost termínu (`KNOWN` = uveden, `UNKNOWN` = neuveden/NULL) a přesný název poskytovatele (`provider`, odpovídá `providers.name`) filtrují všechny odpovídající aktivní výsledky na serveru před stránkováním v přímé i ontologické fázi. Přepnutí stavu či termínu resetuje poskytovatele a načte první stránku; zadání poskytovatele načte první stránku při zachování stavu a termínu. Nápověda názvů pochází jen z načtené sady, ale lze ručně zadat i jiný přesný název. Není to globální facet ani substring search; stejně pojmenovaní poskytovatelé jsou zahrnuti společně. Přepnutí řazení podle nejbližšího uvedeného termínu nepřepočítává relevanci ani způsobilost a platí jen pro načtenou sadu. Neuvedený termín (UNKNOWN) neznamená prošlý termín a při řazení je na konci. Počty nikdy netvrdí celkovou velikost shod.

Volitelný filtr `closesBy=YYYY-MM-DD` vybere výzvy s explicitně uvedeným `submission_close_at` včetně zvoleného kalendářního dne UTC; aplikuje se na D1 před stránkováním v obou FTS fázích a nevytváří závěr, zda je dnes ještě možné podat žádost. Neznámý nebo neparsovatelný termín neprojde filtrem, ale zůstává UNKNOWN, nikoli prošlý. Prázdné/neexistující kalendářní datum, timestamp místo data a opakovaný parametr vracejí `INVALID_CLOSES_BY` 400. Cursor je svázán i s filtrem data, změna data jej zneplatní. Výběr `UNKNOWN` v UI zruší datum uzávěrky; zadání data při zvoleném `UNKNOWN` resetuje dostupnost termínu na všechny termíny. Zrušení chipu data i všech filtrů načte první stránku.

Nativní rozbalovací panel `<details>` se ovládá klávesnicí a na mobilu nevyžaduje hover. Žádné filtry nepřidávají tvrzení o financování ani způsobilosti. Na chybu API a prázdný index se zachovává původní fail-closed stav; E2E scénář používá skutečné API, D1 a seed výzvy, nikoli mock response.

`GET /api/search?intent=…` vrací `nextCursor` (neprůhledný pro klienta, `null` na konci). Následující požadavek pošle stejný normalizovaný záměr, stejné volitelné `status`, `deadline`, `provider`, `closesBy` a `cursor`; výchozí `limit=20`, povolený rozsah 1–50. Chybný limit, cursor, stav, dostupnost termínu, poskytovatel nebo datum vrací 400 (`INVALID_LIMIT` / `INVALID_CURSOR` / `INVALID_STATUS` / `INVALID_DEADLINE` / `INVALID_PROVIDER` / `INVALID_CLOSES_BY`); `CLOSED`, `ALL`, prázdné i opakované hodnoty jsou nepovolené. Poskytovatel navíc odmítá okrajové bílé znaky, řídicí znaky a délku nad 200 znaků; do SQL jde jen parametrizovaně. Nepřítomný status zachovává původní aktivní hledání. Nedostupná DB vrací 503 bez citlivých údajů. Pořadí je deterministické podle FTS rank a ID verze: nejdřív přímé shody, potom širší ontologické shody bez opakování přímých. Cursor je svázán se záměrem, velikostí stránky, stavem, dostupností termínu a přesným názvem poskytovatele, není autentizační token ani snapshot databáze. Při souběžné změně indexu mohou další stránky obsahovat nové/posunuté záznamy; klient duplicitní ID verze při připojování zahodí. Po chybě další stránky zůstává načtená sada viditelná a lze pokus zopakovat. Počet načtených výsledků není celkový počet shod.

Tento navazující úzký slice neuzavírá #400: globální facety, datum od–do, serverové řazení, bezpečně doložené finance filtry a jejich UX/E2E zůstávají otevřené. Obecné konvence pro jiné API endpointy patří do #545, nikoli do tohoto search-specifického kontraktu.
