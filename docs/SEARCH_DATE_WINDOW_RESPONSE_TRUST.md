# Search date-window response trust (#400)

When the user applies an inclusive `closesFrom` or `closesBy` calendar-day bound, the web client checks each returned card against that bound on both the initial and continuation page. A null, invalid, or out-of-window `submissionCloseAt` in a successful API response is treated as an inconsistent response, not as a valid filtered result. The UI shows its existing retry state; on continuation it retains previously validated cards without appending the inconsistent page. A date-only source value compares as its UTC calendar day; a timestamp with an offset compares by its UTC calendar day, independent of the viewer's timezone (matching the API's SQLite `date(...)` window semantics). The original source date text is retained for display.

Verification: `apps/web/src/lib/searchApi.test.ts` covers both endpoints of an inclusive range, malformed/null/out-of-window dates, independent bounds, and pagination. `tests/e2e/core-flow.spec.ts` exercises real D1/API data with a selectively corrupted response, mobile retry to the unmodified API, axe and horizontal reflow. This narrow guard is not full #400 acceptance or a production release gate.
