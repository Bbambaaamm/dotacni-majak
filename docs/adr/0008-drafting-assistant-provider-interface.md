# ADR-0008: Grounded application drafting assistant — provider interface

## Status
Proposed (review pending). Implementation in `packages/drafting/`.

## Context

Issue #362 (M12, P2) asks for a *provider interface* for a grounded
application drafting assistant: help the user draft grant-application
text from their project and a specific grant call — **without changing
dotační podmínky** (official grant conditions).

The acceptance criteria require:

1. **Ownership/authorization je explicitní** — only the project owner may
   use the drafting assistant with project-specific data.
2. **Official facts jsou jasně oddělené od user/AI obsahu** — drafted
   output must carry an explicit label and provenance so AI-generated text
   is never mistaken for official grant terms.
3. **Žádný paywall pro core workflow** — no paid provider is a hard
   dependency; the core workflow degrades gracefully when no provider is
   configured.
4. **Privacy/retention dopad je zdokumentován** — what goes to a provider,
   what is logged, and for how long must be explicit.
5. **Hlavní i chybový scénář má automatické testy** — both success and
   error paths must be covered by automated tests.

The dependency #31 (Application Workspace a readiness model) is CLOSED,
so the workspace domain (`packages/workspace`) is available as the
context for drafting. The drafting assistant sits at the boundary
between the workspace model and an optional AI provider.

## Decision

### 1. Provider is a Protocol, not a hardcoded dependency

`DraftingProvider` is a `typing.Protocol` with two members:

```python
class DraftingProvider(Protocol):
    @property
    def name(self) -> str: ...
    async def draft(context: DraftingContext) -> list[DraftedSegment]: ...
```

This mirrors `EmbeddingProvider` in `packages/search/src/dotacni_majak_search/semantic.py`
(ADR-0005). The core package depends on the Protocol only, never on a
concrete provider. A concrete adapter (OpenAI, Claude, local model, or
a deterministic template-based stub) is a separate, independently-enabled
package.

### 2. No paid hard dependency — provider is optional

`DraftingAssistant.__init__` accepts `provider: DraftingProvider | None = None`.
When `provider is None`, `draft_application_text()` returns an explicit
`DraftResult(available=False, reason="Drafting provider is not configured")`.
This satisfies *Žádný paywall pro core workflow*: the drafting interface,
context contract, and provenance model are fully functional without any
paid provider.

### 3. Context contract — official facts vs user content

`DraftingContext` is a frozen, validated dataclass that structurally
separates:

| Field | Source | Treatment |
|---|---|---|
| `official_facts` | Official grant-call documents | Read-only reference, cited |
| `natural_language_intent` | User | Drafted text is built *from* this |
| `user_notes` | User | Drafted text is built *from* this |

The context carries `grant_call_version_id` so the assistant always
operates against a **pinned** version of grant conditions — never against
a mutable current version. This enforces *ne měnit dotační podmínky*:
draft text references facts about a specific version, it never rewrites
them.

### 4. Draft label + segment provenance

Every drafted output segment carries an explicit `DraftSegmentSource`:

- `OFFICIAL_FACT` — text sourced from an official document; must carry
  `source_reference` for citation (fail-closed at construction).
- `AI_DRAFT` — text generated by the provider; must carry `model`
  identifier for provenance (fail-closed at construction).

The `DraftResult` carries a top-level `draft_label = "AI_DRAFT"` that
marks the entire result as AI-generated. This is the *draft label* from
the issue scope. The result is never presented to the user as official
content.

### 5. Owner authorization is explicit

`DraftingAssistant.draft_application_text()` accepts `owner_user_id` and
`project_owner_id` and raises `DraftingUnauthorizedError` if they do not
match. This mirrors the capability model from ADR-0007, where
`ProjectSharingService.create()` checks `owner_user_id` against
`repository.project_owner(project_id)`.

Authorization is checked **before** any provider call or audit log entry
that would record the request — the denial is fail-closed.

### 6. Fail-closed on provider errors

Any exception from `provider.draft()` is caught and converted to
`DraftResult(available=False, reason="Provider error: ...")`. The caller
receives a clean unavailable result, never a crash. The error type name
(but **not** the message body) is recorded in the audit log for
operator visibility.

### 7. Audit — never stores content

`DraftingAuditEvent` stores only `event_type`, `project_id`, `reason`,
and `created_at`. Segment text, user intent, and project notes are
**never** written to the audit log. This satisfies the PRIVACY.md
constraint *„no sensitive payloads in logs“*.

## Privacy / retention

| Data | Goes to provider? | Logged? | Stored persistently? |
|---|---|---|---|
| `official_facts` (cited text) | Yes — necessary context | No (only event type) | No |
| `natural_language_intent` (user text) | Yes — necessary context | No | No |
| `user_notes` (user text) | Yes — necessary context | No | No |
| `grant_call_id/version_id` | Yes — routing context | No | No |
| Provider error message | No | No (only type name) | No |

**Retention**: The audit repository is injectable; the default
`InMemoryDraftingAuditRepository` is ephemeral. A persistent
implementation (e.g. D1-backed) is a separate integration concern and
MUST define an explicit retention schedule before beta (per PRIVACY.md
and issue #37).

**Provider retention/training policy**: The concrete provider adapter
is responsible for documenting its own retention policy. The core
package has no knowledge of — and no handle to — provider side-effects
beyond the Protocol return value. This satisfies PRIVACY.md: *„minimalizovat
payload, neposílat nepotřebné identifikátory, dokumentovat provider
retention/training policy.“*

## Consequences

- ✅ Provider interface is defined with no paid dependency (Protocol-based).
- ✅ Official facts are structurally separated from user/AI content.
- ✅ Draft label is explicit at result and segment level.
- ✅ Owner authorization is enforced before any provider interaction.
- ✅ Fail-closed: provider errors → unavailable, never crash.
- ✅ Audit never stores content; privacy constraints respected.
- ✅ Automated tests cover happy path, no-provider, error, auth-denied,
  segment validation, max_segments truncation, and audit privacy.
- ⚠️ **UI / accessibility**: No UI component is touched in this slice.
  Per ACCESSIBILITY.md, when a drafting UI is added it must include
  `aria-live` status messages, a clear *draft label* badge, keyboard
  navigation for draft/editing, and a manual accessibility review.
  This is tracked as a follow-up slice (UI is P2, not P0).
- ⚠️ **API endpoint**: A thin API route (`POST /projects/:id/draft`)
  that wires `DraftingAssistant` to the existing owner-capability Bearer
  token auth in `apps/api/src/projectAccess.ts` is a follow-up slice.
  The domain layer here is provider- and transport-agnostic.
- ⚠️ **Concrete provider adapters** (OpenAI, Claude, local template
  engine) are follow-up slices, each independently enabling paid
  features without touching this interface.
